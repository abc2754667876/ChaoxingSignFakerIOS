# 坐标边界与历史数据

当前默认按大陆高德底图处理 MapKit 的拾取值（GCJ-02）。不要因为数据类型是
`CLLocationCoordinate2D`，就把地图拾取值当作 Core Location 的 WGS-84 GPS 值。
国际底图环境可在地图菜单中选择 WGS-84 模式。模式同时用于选点输入和收藏标记输出。

- 大陆地图拾取：GCJ-02 → WGS-84 → 保存到 `savedLocations.v2`。
- 收藏地图标记：WGS-84 → GCJ-02 → MapKit。
- Core Location 当前定位：直接作为 WGS-84 使用。
- 两条签到入口：WGS-84 → GCJ-02 → BD-09，在 `ChaoxingSignLocation` 初始化时统一执行。
- 请求参数和 `locationResult`：共用同一组已取六位小数的 BD-09 值，不再扰动。

地图底图行为会因运行环境不同而变化，因此代码显式提供地图模式，没有用
`CLLocationCoordinate2D` 的类型文档或逆地理编码得到的地址作为判断坐标系的证据。
逆地理编码可能返回较大的 POI 区域，名称相同不能证明坐标精确对应。

## v1 迁移

本仓库中 v1 收藏只有地图选点一个来源，但经历了三种写法：

1. 原版：直接保存地图数值，没有坐标系字段。
2. c0909e6：把地图数值当作 WGS-84，运行 WGS-84 → BD-09 并标为 bd09。
3. 上次修复：原始地图数值标为 wgs84；旧 bd09 数据先逆变换再标为 wgs84。

因此 v1 的标签不能直接当作真实坐标系。迁移先撤销旧版执行的数值变换，
找回原始地图值，再按地图模式转换到真正的 WGS-84。v1 原始字节保留不改写，
结果写入 v2。以后只读 v2，避免再次转换；空 v2 数组也不会重新导入 v1。

此前两个症状在天津示例点的解释：

- 第一版重复执行 WGS-84 → GCJ-02，额外增加向东偏北的位移。
- 上次改成 GCJ-02 提交后，BD-09 显示端再减去百度偏移，组合后接近向南。

回归测试覆盖实际旧收藏字节的三种编码、只迁移一次、备份不变、新数据不重复转换、
地图与 GPS 两条入口提交一致、以及重现上次修复产生的近正南偏移。

https://github.com/ElProfessorFRidg/locus

以上是开源实现作者的证据，不是超星官方接口契约。单元测试验证坐标链路和历史数据修复，
不能代替用户当前设备、当前签到记录中实际经纬度的端到端对照。不能仅凭测试通过声称线上落点已实测。
